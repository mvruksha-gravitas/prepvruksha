## What we are building

An exam-preparation platform for students in India, starting with NEET-UG and later expanding to JEE, KCET and government exams. Launch focus: NEET-UG (Karnataka-first, Kannada + English),
built on a large, human-verified question bank. Core promise: realistic **computer-based
(CBT) mock exams** — NEET moves from pen-and-paper to CBT from the 2027 exam — plus deep
analytics that show students exactly why they lose marks and what to study next.

The same data serves PU colleges, tutorials, teachers and parents through role-based views.

Built and maintained by mVruksha Softwares (solo developer). A separate product from
Vidhyavruksha ERP, connected to it via a small API.

## Tech stack

- **Apps:** Flutter (Dart) — Android/iOS, logged-in web app, admin/review console (Flutter web), Windows exam-lab app (later)
- **Backend platform:** Supabase (Mumbai region) — PostgreSQL, Auth, Storage, Realtime, pgvector
- **Services:** Python 3.12 + FastAPI, packaged as Docker, deployed to Google Cloud Run (`asia-south1`)
- **Import pipeline:** Python worker (Pandoc, PyMuPDF, Mathpix API, Claude API)
- **Public SEO pages:** static HTML generated by a Python script (Jinja2) → Firebase Hosting
- **Push notifications:** Firebase Cloud Messaging
- **DNS:** AWS Route 53
- **CI/CD:** GitHub Actions

## Non-negotiable rules

1. **Answer keys and scoring never come from AI.** They come only from verified, human-reviewed data.
2. **Nothing AI-generated is published without human review.** Questions, explanations, translations and variants all go through `status = 'review'` → a reviewer → `'published'`.
3. **Never send personal data to AI services.** Send only question content and anonymous answer data. No names, phone numbers or emails.
4. **Row Level Security on every table** that holds user or institution data. Test policies for each role.
5. **Business logic lives in `services/api` or Postgres functions**, not scattered in client code. The Flutter apps call the API or Supabase with RLS; they never compute official scores or ranks.
6. **During exams, save answers locally and sync in batches** (every 30–60 s and on submit). Never write to the database on every click. An exam must survive a dropped connection.
7. **Exam patterns are configuration, not code.** Question count, sections, marking, duration and question types come from the `exam_patterns` table.
8. **Portability:** no Firebase Extensions, no Firebase Dynamic Links, no vendor-specific features without a note in `docs/ARCHITECTURE.md`. Core data stays in Postgres.
9. **All data in Indian regions** (Supabase Mumbai, GCP `asia-south1`).
10. **Minors' data:** parental consent is required at signup for users under 18 (DPDP Act). Students control how much detail parents see.
11. **SEO pages are generated only from `published` questions.**

## Conventions

- Dart: follow the conventions already used in Vidhyavruksha ERP where they exist; otherwise `flutter_lints`, Riverpod for state, `go_router` for navigation.
- Python: type hints everywhere, `ruff` + `mypy`, `pytest` for tests.
- SQL: snake_case, plural table names, `uuid` primary keys, `created_at` / `updated_at` on every table.
- Every schema change is a migration in `supabase/migrations/`. Never edit the production schema by hand. Never edit a migration that has been pushed; add a new one.
- Every new table or view needs explicit `GRANT`s for `anon` / `authenticated` / `service_role` in its migration (nothing is granted by default; `supabase/tests/database/03_privileges.test.sql` fails until the table is added to its matrix). Never grant `TRUNCATE`, `REFERENCES`, `TRIGGER` or `MAINTAIN` to API roles.
- Secrets live in Supabase / GCP Secret Manager and local `.env` files that are git-ignored. Never commit keys.
- Keep Kannada and English as first-class: all user-facing strings go through localisation (`intl` / ARB files).

## How to work

- Build in **vertical slices**: one feature working end to end (DB → API → UI → test) before starting the next.
- For any non-trivial feature, propose a plan first and wait for approval.
- When a requirement in `docs/` is unclear or conflicts with code, ask rather than guess.
- Update the relevant doc when a decision changes.

## Commands

Prerequisites: Flutter 3.47 (stable), Supabase CLI, Docker Desktop, uv. Run from the repo root unless noted.

**Database (local Supabase)** — see `supabase/README.md`
```
supabase start                      # local stack; prints URL + publishable key
supabase db reset                   # rebuild local DB from migrations + seed
supabase test db                    # pgTAP RLS / schema tests
supabase db lint                    # schema checks
supabase migration new <name>       # new migration in supabase/migrations/
supabase db push --include-seed     # apply to the linked remote (prepvruksha-dev)
```
Test phone numbers: +91 99999 00001–00005, code `123456` (no SMS sent).

**Flutter** (pub workspace; `flutter pub get` at the root resolves everything)
```
flutter analyze                     # whole workspace
dart format apps packages
cd packages/core && dart test
cd apps/app && flutter test         # likewise apps/console, packages/ui_kit
cd apps/app && flutter gen-l10n     # after editing lib/l10n/*.arb

# run: copy config/<env>.example.json to config/<env>.json first (git-ignored)
cd apps/app && flutter run -d chrome --dart-define-from-file=../../config/local.json
cd apps/app && flutter run --flavor dev --dart-define-from-file=../../config/dev.json   # Android
```
Android emulator + local Supabase: use `http://10.0.2.2:54321` as `SUPABASE_URL`.

**Python services** (`services/api`, `services/pipeline`, `services/seo`; each a uv project)
```
cd services/api
uv sync
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
uv run uvicorn prepvruksha_api.main:app --reload
```

**CI:** `.github/workflows/ci.yml` runs all of the above checks on every PR and push to `main`.
